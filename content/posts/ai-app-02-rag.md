## 🎯 练习目标：为什么需要 RAG

直接问 LLM 三个痛点，RAG（Retrieval-Augmented Generation，检索增强生成）逐一回应：

```
痛点1  幻觉      → 模型不知道的事会编；给它资料，让它"抄着答"
痛点2  知识截止  → 模型训练数据有截止日期；资料是实时的
痛点3  私有数据  → 训练集里根本没有你家文档；检索现查现喂
```

本次练习的语料就用**本站 92 篇技术文章**，目标：做一个"博客问答助手"——问"滑动窗口限流器内存会不会无限增长"，它能基于文章内容回答并指出处。

### 先做一个选型决策：RAG 还是 Function Calling？

上一练（[AI应用练习01：LLM 使用入门](/2026/09/ai-app-01-llm-api/)）的 Function Calling 已经能查数据库了，什么时候用 RAG？判断标准是**数据形态**：

```
结构化数据（订单/职位/订阅数）→ Function Calling 查 SQL，精确、零幻觉
非结构化知识（文章/文档/FAQ）→ RAG 检索+生成，模糊语义匹配
"有哪些IT互联网职位？"        → 工具查表
"限流器内存会不会涨？"        → RAG 查文章
```

两者不互斥：真实客服系统往往是"先路由，工具管事实查询，RAG 管知识问答"。

## 🌟 RAG 的骨架：一条流水线

```
离线（建索引）                      在线（问答）
────────────                      ──────────
文档加载 ──► 切块(chunk) ──► 向量化/建索引
                                    │
问题 ─────────────────────────────►│
                                    ▼
                              检索 top-K 个块
                                    │
                                    ▼
                        拼 Prompt：资料 + 问题
                                    │
                                    ▼
                            LLM 生成（只准依据资料）
```

看起来环节不少，但每一环都可以极简。下面这份 mini-RAG **零第三方依赖**（不用 langchain、不用向量库、不用 embedding 模型），纯 Python 标准库，总共不到 100 行。

## 🌟 手写 mini-RAG

### 第一步：切块（chunking）

92 篇文章不能整篇塞进 prompt，要切成"知识块"：

```python
docs = []
for path in sorted(glob.glob("/path/to/posts/*.md")):
    raw = open(path, encoding="utf-8").read()
    text = re.sub(r"^---\n.*?\n---\n", "", raw, flags=re.S)   # 去 frontmatter
    title = re.search(r'^title:\s*"(.*)"', raw, re.M).group(1)
    # 按 ## 标题切块——标题天然是语义边界，比定长瞎切强得多
    for sec in re.split(r"\n(?=## )", text):
        sec = sec.strip()
        if len(sec) < 80:                    # 太碎的块没检索价值
            continue
        chunks = [sec] if len(sec) <= 900 else \
            [sec[i:i+900] for i in range(0, len(sec), 820)]   # 超长块二分，留80字重叠
        for c in chunks:
            docs.append({"title": title, "text": c[:1000]})
```

切块策略三原则：**沿语义边界切**（标题/段落）、**块别太大**（检索要的是"命中要说的话"，不是整篇）、**相邻块留重叠**（防止答案恰好被切走）。本站 92 篇 → **4615 个块**。

### 第二步：中文免分词的 BM25 索引

理想检索是向量（语义），但 embedding 服务不一定有——我用的网关 `/v1/embeddings` 直接返回 501 Not Implemented。这不是终点：**BM25 先跑通，向量是可插拔的升级项**。中文 BM25 的免分词技巧：**字符二元组（bigram）当词**：

```python
def tokenize(s):
    s = re.sub(r"[^\w\u4e00-\u9fff]+", " ", s)
    toks = [w.lower() for w in re.findall(r"[a-zA-Z0-9_]+", s)]  # 英文整词
    han = re.sub(r"[^ \u4e00-\u9fff]", "", s)
    toks += [han[i:i+2] for i in range(len(han) - 1)]             # 中文二元组
    return toks
```

"滑动窗口" → "滑动/动窗/窗口"，查询和文档用同一套切法，匹配照样成立。BM25 打分本体（k1=1.5, b=0.75 是公认默认值）二十行搞定，完整代码在练习仓库 `02-rag/exp_rag.py`。

### 第三步：检索的真实成绩单

五个真实问题，4615 个块，纯 Python 单线程：

```
Q: 生产者消费者为什么用while不用if      (111ms)
  51.13  [Java并发练习01：手写生产者-消费者…]  ← 正确命中
  36.58  [数据结构详解：队列(Queue)…]
  33.52  [Java并发练习01…]（另一节）

Q: 滑动窗口限流器内存会不会无限增长     (101ms)
  49.74  [Java并发练习02：手写滑动窗口限流器…]  ← 正确命中
  41.47  [Java并发练习02…]（离生产还有多远一节）
  36.05  [多租户系统设计实战…]（限流兜底一节）

Q: 多租户报表为什么不能直接在主库GROUP BY  (109ms)
  45.24/41.84/38.99  [多租户系统设计实战…] 三连命中

Q: TCC模式有几个阶段                  (98ms)
  19.51  [分布式系统核心模式详解：TCC…]  ← 正确命中

Q: 栈和队列的区别是什么                (106ms)
  21.45  [数据结构详解：队列…]  ← 命中相关文
```

五个问题 top-1 全部命中正确文章，单次检索约 100ms。注意分数的启示：**分数绝对值没有意义，分数差才有**——top1 与 top2 拉开 10 分以上的，检索基本稳了；挤在一起的就要小心。

## 🌟 翻车实录：模型说"资料被截断"

第一版脚本有个偷懒写法：为了打印日志好看，喂给模型的是每个块的**前 80 个字符**。检索明明命中了，模型却回答：

> **资料里没有直接、完整地讨论这个问题**……（资料被截断，"翻车"的具体细节和事故表现没有给出，无法确认是否就是内存问题）……

模型没说错——它只看得见 80 字，当然"没有完整讨论"。这是 RAG 最典型的工程坑：**检索命中 ≠ 上下文可用**。切块逻辑、注入 prompt 的截断、块与问题相关的部分没切进来，任何一环缩水，检索分数再高也白搭。修复：把完整块内容（本例 ≤1000 字）喂进去，同一个问题的回答立刻变成：

> **取决于实现版本，资料里两种做法结论完全不同：**
> **1. 日志版（逐请求记时间戳的写法）——内存会随流量增长**。资料2明确指出：这种"逐请求记时间戳"的滑动窗口日志版，占内存与请求数成正比……
> **2. 分桶版（Sentinel 的做法）——内存不会随流量增长**。把 1 秒切成 20 个 50ms 的桶，每桶只存一个计数，内存与请求数无关，只与桶数有关……
> 至于日志版在流量持续增长时内存是否"无限"增长，资料里没有更细的说明。

三个细节值得品味：回答**引用了资料编号**（可追溯）；给出了**对照表**；最后一句**主动承认资料边界**——不编造，这正是 RAG 的品格。

## 🌟 对照实验：无检索 vs 有检索

同一个问题"滑动窗口限流器内存会不会无限增长"，直接问模型（无检索）：

> （模型输出了一篇约 2000 token 的通用长文：自己写了 Python 版限流器、Redis Lua 脚本、分桶方案……）

内容不算错，但全是**参数记忆里的通用知识**——不是本站文章说的那三版演进，也和"我们"的代码无关，还包含大段没用到的代码块。有检索的回答则句句来自资料、带出处、承认盲区。

| 维度 | 无检索 | 有检索 |
|---|---|---|
| 事实来源 | 参数记忆（通用、泛化） | 指定语料（私有、精确） |
| 可追溯 | 无出处 | 引用资料编号 |
| 盲区处理 | 不知道也答得头头是道 | 明说"资料里没有" |
| 长度 | 容易失控（2000+ token） | 被资料框住，紧凑 |
| 成本 | 输出长=贵 | 输入多 token、输出短 |

## 🧭 进阶路线：从 BM25 到工业级 RAG

mini-RAG 证明了骨架，生产化要补四课：

1. **向量检索**：BM25 靠字面重叠，"机器挂了"搜不到"服务不可用"。Embedding 把语义压成向量，余弦相似度匹配。等价的接口（`/v1/embeddings` 或本地 sentence-transformers）接上后，索引层换实现即可——所以第一步就把检索抽象成函数是对的；
2. **混合检索 + 融合**：BM25（精确词、专有名词强）+ 向量（同义改写强）各取 top-K，用 RRF（倒数排名融合）合并。两者是互补不是替代，工业系统基本都走混合；
3. **Rerank 精排**：召回 top-50 后用交叉编码器（如 bge-reranker）重排取 top-3，精度普遍再涨一截。粗召回求快、精排求准，两级分工；
4. **评测先于调参**：没有 hit rate / MRR 数字，一切"感觉变好了"都是玄学。攒 50 个真实问题+标准出处，先测 BM25 基线，每加一层（向量/融合/精排）跑一遍对比——**检索质量决定 RAG 上限，生成模型只是守住了这个上限**。

## ⚠️ 踩坑清单

1. **检索命中就以为万事大吉** → 本次翻车主坑：注入 prompt 的内容被截断，模型看得见的才算数；
2. **定长切块** → 答案被切两半两边都检索不强；沿标题/段落等语义边界切+重叠；
3. **中文不做处理直接按"词"算** → 中文没空格，字符 bigram 是免分词的最小可行方案，上分词库（jieba）是下一档优化；
4. **只看检索分数不看分数差** → top1/top2 挤在一起的答案要降权或触发追问；
5. **Prompt 不设"资料不足就说不知道"** → 模型会拿资料当参考、拿记忆当答案，幻觉从侧门进来；
6. **一上来就 langchain+向量库全家桶** → 先 BM25 跑通骨架、攒评测集，再逐层升级，出问题才知道是哪层的锅；
7. **结构化数据也硬上 RAG** → "查个数"用 Function Calling/SQL，RAG 管非结构化知识，选型错了事倍功半。

## 📝 练习收获

- RAG 的本质一句话：**先查后答，把"闭卷考试"改成"开卷考试"，并把"抄哪里"亮出来**；
- 100 行标准库就能搭出可用的 RAG 骨架，难的不是框架是工程细节：切块、截断、分数差、资料边界；
- 检索层可插拔（BM25 → 向量 → 混合 → 精排），但**评测集要第一天就建**，否则升级全靠手感；
